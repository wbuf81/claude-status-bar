## The goal

Not a single swapped icon — a small state machine with a personality. Daisy reacts to what
Claude Code is actually doing, gets sleepier the longer she's idle, and has enough random
variance that the resting icon is never truly static.

Art comes from Grok Imagine / Google Gemini (Nano Banana), generated by the user from the
prompts in `DAISY-PROMPTS.md`. Claude cannot originate images — it can only transform supplied
ones — which is why the prompt-handoff approach was chosen.

### Key implementation details

- **Animation styles** are an enum at `main.swift:376`:
  `enum AnimStyle: String { case web, code, crab }` — surfaced in the menu at `main.swift:690`
  as "Claude Spark" / "Claude Code" / "Crab Walking".
- **"Claude Code" style uses no images** — it tweens text glyphs `["✻","✽","✶","✳","✢"]`
  (`main.swift:414`), scaling each down to `codeDip` and back.
- **Frames are base64 PNG strings compiled into the binary**, decoded once and cached lazily
  (`decodePNGs`, `main.swift:1329`). No asset catalog, no external image files at runtime.
- **Two color modes**, `iconColor` at `main.swift:413`: brand Orange, or `nil` meaning System —
  an adaptive black/white template image that macOS recolors for the menu bar automatically.
- **Frame rate is per-style**, `fps` at `main.swift:430`. Crab runs 12.5fps to match its source
  GIF's 0.08s delay.
- **Icon renders ~18pt tall** — about 36px on a Retina menu bar. This is the binding constraint
  on all art.

### The System-mode gotcha (important)

`adaptiveCrabFrame` in `CrabRender.swift` builds template images by mapping **brightness to
opacity**: pixels below `darkCut = 0.30` become fully transparent holes, brightness from there
up to `bodyLevel = 0.54` ramps gray→solid. That works for the crab (bright orange body stays
solid, dark eyes punch through as negative space).

**It would destroy a Bernese.** A black body has luminance ~0.05, so it would vanish entirely,
leaving a floating white chest patch and nothing else.

**Fix:** for Daisy, build the template from the **alpha silhouette** instead — solid ink in the
shape of the dog, with eyes and the muzzle blaze punched out as holes for definition. Do not
reuse the brightness mapping. Leave `adaptiveCrabFrame` alone so the crab still works.

## Art spec

**Style: 16-bit pixel art, Stardew Valley / SNES era, authored at ~48x36 px per frame.**

### Why pixel art — tested, not assumed (2026-08-04)

The first character sheet was flat-vector chibi and looked great at full size. A legibility test
(downsample to 36/28/22px, plus an alpha-silhouette render simulating System mode) found:

- **Full color at 36px survived better than expected** — soft, but blaze, rust legs, and white
  paws still read.
- **The silhouette collapsed to an unreadable black blob.** Every identifying feature — blaze,
  chest bib, eye — is white, so it vanished into the alpha shape. Not fixable in post; the
  information isn't in the image.

Pixel art fixes both: authored at final size so it's never resampled (no LANCZOS mush), and it
forces deliberate authoring of negative space the way the upstream crab does with its eyes
(`CrabRender.swift` calls them "negative-space eyes").

Test artifacts are in the scratchpad: `key.py`, `shrink.py`, `legibility.png`.

### Rules

- **Transparent background via a real alpha channel**, or flat pure magenta `#FF00FF` as a
  chroma-key fallback. No magenta exists in a Bernese, so it keys cleanly.
- **Watch for FAKE transparency.** The first attempt painted a gray checkerboard into RGB with no
  alpha channel at all — it looks correct and isn't. Always verify the alpha channel exists.
- **Crisp integer pixel grid, no anti-aliasing.** This is the #1 failure mode of image models
  asked for pixel art: they emit high-res images that look pixelated but have non-integer,
  misaligned, anti-aliased blocks. The pipeline includes a grid-snap step to rescue near-misses.
- **Strict 8-color palette**, no gradients, no dithering (reads as noise at 36px).
- **All white and rust markings must be bold connected shapes ≥2px thick** so they survive as
  negative space in System mode. No 1px details, no speckles.
- **No ground shadow, no drop shadow** — wrecks the alpha silhouette.
- **4 frames per animation, 6 for run cycles.** Every extra frame is another chance for the model
  to mangle a leg.
- **Same pixel scale, same position, fixed camera** across a strip. Drift reads as vibration.
- Markings must be spelled out explicitly every time; "Bernese Mountain Dog" alone yields a
  generic dog roughly half the time.

**Workflow:** generate the character sheet (Prompt 0) first, iterate until happy, then attach it
as a reference image to every subsequent prompt. Character consistency is the whole ballgame.
Gemini / Nano Banana is better at reference-conditioned consistency and transparent PNG output;
Grok Imagine is better for exploring the initial look.

### Measured facts about the approved sheet (verified, not assumed)

- **Delivered as 960x960 RGB with NO alpha channel** — the "transparency" is a gray checkerboard
  painted into RGB. Second time this happened. Recoverable via border flood-fill (the black
  outline stops the fill) but fragile: if a background gray ever matches a dog gray, the fill
  punches a hole through her. **Demand magenta `#FF00FF` on the animation strips.**
- **Native grid is 100x100 logical pixels**, upscaled to 960 (960/100 = 9.6, so blocks alternate
  9 and 10 screen px — this exact histogram is how the grid was detected). Recover by sampling
  the centre of each logical block, NOT by resampling.
- **Each dog is ~32x38 logical pixels** — essentially 1:1 with the ~36px menu bar target, so no
  downsampling is needed at all. This is the whole win over the vector version.
- **The art is NOT clean 8-colour pixel art.** It contains anti-aliasing / blend tones that do
  real work softening black↔white transitions. A recolour experiment that treated the taupe
  `(157,129,114)` as a rust marking splattered rust across the tail and body — because that tone
  is a blend pixel, not a marking. **Quantize to ~16 colours, not 8.** Forcing 8 looks worse.
- The three dogs sit adjacent with **touching/overlapping bounding boxes**, and there are stray
  1-2px specks around each. Speck filter at `minblob≈40` cleans them.

### PROVEN PROMPT RECIPE (learned the hard way, 2026-08-04)

The first trot attempt produced **6 frames with only ~3 distinct poses** — f2 vs f3 measured **2.0%
different**. Cause: the prompt described the cycle as a *concept* ("legs move through a full
diagonal trot"), so the model drew "a trotting dog" six times.

**The fix, validated:** describe **every frame explicitly and separately**, and state the motion
budget. Rewriting the trot as 4 explicitly-described, heavily exaggerated poses
(FULL STRETCH / LANDING SQUASH / GATHERED HOP / PUSH OFF) produced pairwise differences of
**30–56%** — a real cycle.

**Two opposite recipes depending on the animation:**

| | high-motion (run, zoomies, dig, wag) | subtle idle (sleep, blink) |
|---|---|---|
| framing | "dramatically and obviously different, exaggerate heavily, do not repeat a pose" | "nearly identical, change ONLY the pixels described, leave everything else identical" |
| target pairwise diff | adjacent pairs >12%, none <8% | adjacent pairs ~2–8% |
| failure mode | duplicate poses | a thrashing, restless dog |

Also proven necessary: **4 frames, not 6** (fewer frames with bigger deltas read better at 36px and
are an easier ask), and **grid layout, not a single strip** — 6-across forces a ~6:1 image and the
model shrinks her. Use 2x2 for 4 frames, 3x2 for 6.

**Magenta works perfectly.** Flat `#FF00FF`, clear gaps, correct scale, crisp grid all came back
right first time once asked for explicitly. Key with a generous threshold
(`r>130 and b>130 and g<110`) — a tighter one left a stray speck.

### Frame alignment: NOSE-ALIGN (decided 2026-08-04)

Frames arrive in independent grid cells with inconsistent placement, so they must be re-aligned onto
a shared canvas. Three strategies were built and compared as GIFs; **nose-align won** (user's call,
viewing `align_compare.gif` / `align_native.gif`).

- **nose-align** — pin the rightmost pixel (muzzle) and the topmost pixel (ears), let body and legs
  move underneath. Use for **locomotion**: trot, zoomies, sniffing, digging.
- **centroid-align** — use for **idle poses** (sleep, blink, belly-up) where there's no meaningful
  muzzle anchor on a curled body.
- **bottom-align** — rejected; frame heights vary (27px vs 32px on the trot) so she pogos.

Measured on the approved trot: all 4 frames had `head_y = 0` (ears topmost) and nose at a stable
37–42px, which is why nose-align is well-conditioned.

### System-mode template: SOLVED

The blob problem from the vector attempt is fixed. Build the template as **ink where opaque, with
pixels brighter than a luminance cut punched through as transparent holes.** The white blaze, chest

dog in monochrome.

**Tuned value: luminance cut = 150.** (110 leaves the bib underdefined; 190 is close but slightly
over-punches.) Verified across both the side profile and three-quarter views at native and 36px.

Test scripts in the scratchpad: `analyze.py` (alpha + palette), `grid.py` (block-size detection),

`legibility3.png`, `rust.png`.

## Alignment: hard-won rules

Frames arrive at inconsistent positions inside their grid cells, so each one is re-positioned by a
feature of the dog. Getting this wrong produced every "looks a bit off" complaint in review.

**Never align on the centre of mass.** Whatever moves drags the centroid with it, so aligning on the
centroid *compensates for the motion and cancels it*. The ear-perk fidget measured 22% different in
the source sheet and came out at 6.5% — nearly invisible — purely because of this.

**Align per-frame, fit per-clip.** An earlier version clamped each frame individually to keep it on
canvas, which silently overrode alignment by a different amount on every frame: the wag's mirrored
frame shifted 0 px while its neighbours shifted 7–8. That was the visible jitter.

**Measure content, not the dog.** Particles sit outside the dog's bounding box — a risen sleep Z,
dirt thrown wide. Sizing the canvas from the dog alone silently dropped both large ZZZs and clipped
the digging dirt.

**Mirror in source space, never on the finished canvas.** A canvas flip maps `x → CW-1-x`, which
shifts an even-width sprite half a pixel.

**Do not mirror a front view to fake a new pose in an ANIMATION.** She measures 31.6% different from
her own mirror, so a flip swings her whole body, not just her tail. It looks completely fine as a
still image and reads as a twitch in motion — this cost two review rounds.

| clip family | alignment | why |
|---|---|---|
| trot, zoomies, dig, sniff | `nose` — muzzle + ear line | her head holds still, legs do the moving; frame heights vary 5 px so pinning her feet makes her pogo |
| sleep, drowsy, alert, ask, wag | `ground` — ground line + head centre | all ground-contact poses; head centre because a sweeping tail would otherwise drag her sideways |
| yawn | `ground-front` — ground line + front end | in a downward-dog her raised *rump* is the top of the sprite, so "top rows are her head" is false |

## One motion at a time

At 21 pt, two simultaneous motions read as noise. The wag originally asked for a sweeping tail **and**
a body bouncing 3–4 px, and no amount of frame-rate tuning fixed it — the body region was changing
~48% every frame. When prompting a new clip, pick the single thing that moves and explicitly lock
everything else: *"every pixel of her except X is identical between frames."*

Final frame rates after menu-bar review: **trot 6.5** (called "perfect" and left alone), zoomies 9.5,
**dig 4.5**, **sniff 4.5**, wag 4, ask 3.5, sleep 3, drowsy 2.5, yawn 2.2, alert 1.4. Every clip was
slowed from its first guess, most of them twice — first guesses were consistently too fast.

## Sizing: she is already at the ceiling

Measured, not assumed: `NSStatusBar.system.thickness` is **22 pt**. Crisp rendering needs one logical
pixel per device pixel (0.5 pt/px), which caps the sprite at 44 device px; her tallest pose is 42. So
she cannot be made meaningfully larger and stay crisp.

"She looks small" came from the canvas being sized by her tallest pose. Sitting is 42 px, lying is
~30 px, so an idle pose rendered ~15 pt of dog in a 21 pt slot while neighbouring icons show ~18 pt.

The fix is `MAX_UPSCALE` in `tools/make_frames.py` (currently **1.15**): short clips are scaled up
toward the canvas height, tall ones left alone. This RESAMPLES and cannot avoid it — a 30 px sprite
has no integer scale between 1x (15 pt) and 2x (30 pt, far over the bar). NEAREST is used rather than
a smooth filter, leaving some pixels 1 device px and some 2, which reads better on pixel art than
uniform blur. Set to 1.0 to revert to strictly crisp, physically-consistent scaling.

Scaling is per CLIP, never per frame (per-frame would make her pulse). Clips keep a **shared height**,
which is what preserves the common ground line, and get their **own width**, since the status item is
variable-length and a shared width would pad every clip out to the widest.

For quick experiments without regenerating: `defaults write com.local.claudestatusbar daisyHeight 24`
then relaunch; `defaults delete …` to revert.

## Known rough edges

1. **Icon is 21 pt tall, upstream's other styles are 18 pt.** Her tallest pose is 42 logical px, and
   18 pt would mean a 0.86x non-integer downscale that smears the pixel art. Crisp-but-taller was the
   deliberate trade. If it looks wrong beside the crab, options are: crop 2 px off the three sitting
   poses to reach 20 pt, or accept the blur.
2. ~~Alignment changes between clip families.~~ **FIXED.** All ground-contact clips now share one
   ground line, so her feet no longer shift when the state changes.
3. **The curled sleep pose is nearly a solid blob in System mode** — her bib is hidden underneath, so
   there is no internal detail to punch out. The ZZZ is what makes it read.
4. **`drowsy` is a 2-frame blink** because the generated half-lidded frame was a duplicate. Fine at
   this size; a synthesised mid-frame is possible if it looks abrupt.
